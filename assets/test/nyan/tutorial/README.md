# Tutorial scenario nyan fixtures + stopgap schemas (MVP)

This directory is the **tracked source of truth** for the hand-written nyan data
that the Phase 0 `--tutorial` scenario needs. These files are **not** converter
products and **not** generated by `convert-export-api` (api_export). They are a
hand-authored stopgap so the tutorial (16×16 grass map, 1 villager, 1 town
center) can load and the player can select and move the villager.

## Why this exists

The `engine` modpack under `assets/converted/engine/` is `.gitignore`d (it is
regarded as generated/copyrighted asset output). The tutorial scenario,
however, needs six nyan files that are **hand-written** and therefore cannot be
regenerated by the converter or api_export. Without tracking them, a clean
checkout cannot reproduce the tutorial scenario — it would depend on machine-
local ignored files. This directory fixes that by keeping the hand-written files
in a tracked location and providing an install step that copies them into the
runtime location.

## The six files

### Fixtures (scenario data, hand-written)

| Source                                  | Runtime (`assets/converted/engine/util/`)        |
|-----------------------------------------|---------------------------------------------------|
| `fixtures/tutorial_data.nyan`           | `tutorial_data.nyan`                              |
| `fixtures/setup/tutorial_setup.nyan`    | `setup/tutorial_setup.nyan`                       |
| `fixtures/scenario/mission_1.nyan`      | `scenario/mission_1.nyan`                         |

### Stopgap schemas (hand-authored additions that api_export does not emit)

| Source                       | Runtime                  | Adds                                                                  |
|------------------------------|--------------------------|-----------------------------------------------------------------------|
| `schemas/game_entity.nyan`   | `game_entity.nyan`       | `PlacedEntity` (entity + tile position, used by `Scenario.initial_entities`) |
| `schemas/scenario.nyan`      | `scenario.nyan`          | `Scenario` class (`size`, `terrain_chunks`, `initial_entities`) — api_export does not emit this file at all |
| `schemas/terrain.nyan`       | `terrain.nyan`            | `Size` (x/y) and `TerrainChunkLayout` (offset/size/tile_fqons)        |

`game_entity.nyan` and `terrain.nyan` are emitted by api_export **without** the
stopgap classes; `install.sh` overlays the hand-written versions on top of the
generated base. `scenario.nyan` is entirely hand-written (api_export does not
emit it).

## Reproduce the tutorial on a clean checkout

```bash
# 1. Build the engine (see repo build docs).

# 2. Generate the base engine schemas (the ~56 api_export nyan files).
python -m openage convert-export-api assets/converted

# 3. Overlay the 3 stopgap schemas and add the 3 scenario fixtures.
bash assets/test/nyan/tutorial/install.sh

# 4. (optional) sanity-check that the scenario loads.
bash assets/test/nyan/tutorial/validate.sh

# 5. Run the tutorial.
bin/run --tutorial --no-prompts
```

## Validate

`validate.sh` runs `bin/run --tutorial --no-prompts`, confirms the log shows

```
load_scenario: engine.util.scenario.mission_1.Mission1 size=16x16 chunks=4
load_scenario: engine.util.scenario.mission_1.Mission1 initial_entities=2
```

and that no nyan `LangError`/`NameError`/`MemberNotFoundError`/... appears.

## Scope and known limitations (Phase 0)

- These are a **Phase 0 stopgap**. The proper long-term solution is to teach
  `api_export` (or the converter) to emit `PlacedEntity`, `Scenario`,
  `TerrainChunkLayout`, and `Size` as first-class engine schema, and to source
  the scenario fixtures from a real campaign/scenario pipeline. That is
  **out of Phase 0 scope** (do not modify the converter in Phase 0).
- `install.sh` overlays the stopgap `game_entity.nyan` / `terrain.nyan` over
  the api_export output. If a future api_export changes the base content of
  those two files, the overlay here must be re-derived (re-apply the stopgap
  additions onto the new base).
- The fixtures deliberately carry **only** the data needed to load the Phase 0
  scenario (movement). Attack / gather / build / train / research data is
  intentionally absent and is Phase 1 work.
- Selection and movement of the spawned villager still require **manual**
  verification at the display: `bin/run --tutorial --no-prompts` opens a window
  with the 16×16 map, 1 villager and 1 town center. `validate.sh` proves the
  scenario loads and the window renders; it does not click.
