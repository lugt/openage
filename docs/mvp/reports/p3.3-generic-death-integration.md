# William Wallace Mission 1 — P3.3 Generic Death Integration

**Phase:** P3.3 — Generic death event  
**Branch:** `mvp/william-wallace`  
**Date:** 2026-07-29  
**Companion spec:** `docs/mvp/specs/WW_MISSION1_SCENARIO_RUNTIME_SPEC.md`  
**Companion plan:** `docs/mvp/specs/WW_MISSION1_DEVELOPMENT_PLAN.md`

P3.3 replaces the inline HP<=0 / `remove_game_entity` check (which lived in
`ApplyDiscreteEffectHandler` during P3.2) with a generic DeathEvent that
fires for any source of damage and is idempotent across duplicate
dispatches.

---

## Before / after call chains

### Before (P3.2)

```
ApplyDiscreteEffectHandler (game.apply_discrete_effect)
 → stale-event safety
 → target_live->set_attribute(time, attribute_fqon, current - amount)
 → if (new_value <= 0):
     → gstate->remove_game_entity(target_id)    [INLINE DEATH/REMOVAL]
```

### After (P3.3)

```
ApplyDiscreteEffectHandler (game.apply_discrete_effect)
 → stale-event safety
 → target_live->set_attribute(time, attribute_fqon, current - amount)
 → if (new_value <= 0):
     → create_event("game.death", time, {target_id})    [DISPATCH]
DeathEventHandler (game.death)                                  [NEW]
 → stale-event safety
 → if (entity->mark_dead() == false): return                 [IDEMPOTENT]
 → gstate->remove_game_entity(target_id)                      [SINGLE OWNER]
 → stop_attackers(target_id)                                  [NEW]
```

`AttackHandler` no longer participates in the death decision at all.
It only dispatches `game.attack` (the follow-up re-evaluation) and
`game.apply_discrete_effect` (the per-hit damage). Death is now a
**side-effect of the Live attribute write**, not a side-effect of the
attack pipeline.

## New GameEntity / Live API

### `GameEntity::is_dead() / mark_dead()`

```cpp
bool is_dead() const;          // reads dead flag
bool mark_dead();              // sets flag; returns true on first call,
                               // false on subsequent calls (idempotent)
```

The flag is private to the entity; `mark_dead()` is the only way to
flip it. This gives `DeathEventHandler` a single, race-free check for
"have we already processed this death?".

### `Live::on_threshold_drop(attribute, threshold, callback)`

```cpp
using threshold_callback_t = std::function<void(int64_t new_value)>;
void on_threshold_drop(const nyan::fqon_t &attribute,
                       int64_t threshold,
                       threshold_callback_t callback);
```

A **one-shot per Live per attribute** listener that fires when the
attribute's post-write value drops to `<= threshold`. Once the listener
fires, it is permanently disarmed (does NOT re-arm if the value goes
above threshold and back down). The callback fires inside `set_attribute`
after a successful write, so the listener sees the post-write value.

The API is provided for future scripted effects (P5+) — the P3.3
death path uses direct `create_event("game.death")` dispatch from
`ApplyDiscreteEffectHandler` because the effect handler already
carries the EventLoop / State / time / attribute-fqon context, but the
threshold API is available for any future "if attribute drops to X,
fire Y" pattern.

## Idempotency guarantees

| Scenario | Result |
|---|---|
| HP 25 → -5 from one effect | 1 death event dispatched; 1 mark_dead → true; 1 remove_game_entity |
| HP 25 → -5 from same-timestamp double effect | First effect: write -5, dispatch death. Second effect: target gone → no-op. (Even if both effects fire before any death event, the death handler's mark_dead gate returns false on the second event.) |
| HP 25 → -5 → +5 → -5 | 1 death event total (listener disarmed after first trigger; mark_dead stays true) |
| Already-dead entity receives new effect | `has_game_entity(target_id)` returns false → "stale event, dropping" |
| Non-Attack source dispatches `game.apply_discrete_effect` directly | Effect handler runs, dispatches death on threshold cross (same path as Attack-sourced damage) |
| Multiple attackers on the same target; one attacker lands the killing blow | First kill dispatches one death event; `stop_attackers` cancels every attacker whose `Attack.target_id == killed_id` |

## P3.3 invariants introduced

| Invariant | Implementation |
|---|---|
| Death fires at most once per entity | `GameEntity::mark_dead()` returns true on first call, false on subsequent |
| Same-time multiple effects → one death | mark_dead gate + first effect's remove makes subsequent effects see "stale target" |
| Dead target receiving new effect is a safe no-op | `has_game_entity(target_id)` returns false → log + return |
| Non-Attack damage source also triggers death | All combat damage routes through `ApplyDiscreteEffectHandler` regardless of source |
| Attack follow-up after target death stops | `stop_attackers()` iterates GameState and calls `Attack::stop_attack()` for every attacker pointing at the killed target |
| `AttackHandler` does not decide death | AttackHandler no longer reads HP or checks `<= 0`; it only dispatches follow-up events |

## P3.3 TEMPORARY items

The following exist in P3.3 but will be REMOVED by P3.4:

1. **Synchronous `remove_game_entity` in `DeathEventHandler`.** P3.4
   replaces this with a deferred `RemovalEvent` so the dispatcher's
   call stack never mutates the GameState entity container
   mid-iteration. Until then, `DeathEventHandler` is the single owner
   of the removal call.
2. **HP allowed to go negative before death.** Same as P3.2; the
   threshold transition fires after the curve write lands the value
   below 0 (e.g. 1 → -5). Future scripted-effect work may use the
   threshold listener API to dispatch death BEFORE the curve dips
   (e.g. via a script-level "apply -amount and check" wrapper).

## P3.4 readiness

P3.4 must:

1. Remove the synchronous `gstate->remove_game_entity(target_id)`
   from `DeathEventHandler::invoke`.
2. Replace it with `create_event("game.removal", time, {target_id})`.
3. Implement `RemovalEventHandler` that performs the removal at a
   safe point in the event loop (after the current batch settles).
4. Cover:
   - stale attack follow-up after removal
   - stale effect event after removal
   - duplicate removal events → no-op
   - multi-attacker scenario (only one removal)
   - safety under EventLoop iteration (no iterator invalidation)

The P3.3 report explicitly pins the readiness:
- The synchronous removal is isolated in a single line at
  `death.cpp:75` (well-marked "P3.3 single owner; P3.4 replaces").
- The idempotency gate (`mark_dead`) is already in place, so
  multiple death dispatches will produce at most one removal event.
- `AttackHandler` already detects "target gone" via
  `has_game_entity(target_id)` and stops cleanly — P3.4 just needs
  to verify the post-removal path is still safe.
