# William Wallace Mission 1 — P3.2 Damage-Effect Integration

**Phase:** P3.2 — Route damage through effects  
**Branch:** `mvp/william-wallace`  
**Date:** 2026-07-29  
**Companion spec:** `docs/mvp/specs/WW_MISSION1_SCENARIO_RUNTIME_SPEC.md`  
**Companion plan:** `docs/mvp/specs/WW_MISSION1_DEVELOPMENT_PLAN.md`

P3.2 routes combat damage from direct `Live::set_attribute` writes inside
`AttackHandler` to a dedicated `ApplyDiscreteEffectHandler` event. The
refactor preserves the P3.1 characterization (5 hits, 25→19→13→7→1→-5,
cooldown=2.0 s, removal at t=21.28976) while removing the "AttackHandler
owns Health mutation" coupling.

---

## Before / after call chains

### Before (P3.1)

```
SendCommandHandler (game.send_command)
 → add_command(AttackCommand) + create_event("game.attack")
AttackHandler (game.attack)
 → pop AttackCommand
 → range check; not in range → Move::move_default + create_event("game.attack", t+move_time)
 → in range, cooldown elapsed:
   → target_live->set_attribute(time, health_fqon, current - damage)   [DIRECT HP WRITE]
   → if new_value <= 0: gstate->remove_game_entity(target_id)           [INLINE DEATH]
   → create_event("game.attack", t+cooldown)
```

### After (P3.2)

```
SendCommandHandler (game.send_command)
 → add_command(AttackCommand) + create_event("game.attack")
AttackHandler (game.attack)
 → pop AttackCommand
 → range check; not in range → Move::move_default + create_event("game.attack", t+move_time)
 → in range, cooldown elapsed:
   → create_event("game.apply_discrete_effect", t, {target_id, amount, attribute_fqon})   [DISPATCH]
   → create_event("game.attack", t+cooldown)
ApplyDiscreteEffectHandler (game.apply_discrete_effect)                [NEW]
 → stale-event safety: if target gone, log and return
 → target_live->set_attribute(time, attribute_fqon, current - amount)  [SINGLE WRITER]
 → P3.2 temporary: if new_value <= 0, gstate->remove_game_entity(target_id)   [P3.3 REPLACES]
```

The AttackHandler no longer imports `Live` (it still queries the Attack
component for `damage` and `health_attribute_fqon`, but does not mutate
the target Live component). The single HP writer is now
`ApplyDiscreteEffectHandler::invoke`.

## P3.2 TEMPORARY items

The following exist in P3.2 but will be REMOVED by later phases:

1. **Inline removal in `ApplyDiscreteEffectHandler`** (`apply_discrete_effect.cpp`,
   `if (new_value <= 0) { gstate->remove_game_entity(target_id); ... }`).
   This is the "old death path" that previously lived in AttackHandler.
   P3.3 replaces it with a generic `DeathEvent` derived from a Live
   threshold/dependency; P3.4 then defers the actual entity removal to a
   separate `RemovalEvent` so the dispatcher's call stack never mutates
   the GameState entity container mid-iteration.

2. **HP allowed to go negative.** During P3.2 the curve can hold values
   like -5 (the 5th hit drops HP from 1 to -5 before removal). This is
   acceptable per spec §P3.2 ("temporarily allow Health to become
   negative"); P3.3 introduces a threshold/dependency that triggers
   death BEFORE the curve dips, but the curve itself remains capable of
   holding negative values to support scripted future effects.

## Stale-event semantics introduced (P3.2)

| Scenario | Behaviour |
|---|---|
| Effect event target was removed between scheduling and invocation | Handler logs "stale event, dropping (no-op)" and returns; no throw, no GameState mutation |
| Effect event target has no Live component | Handler logs "dropping (no-op)" and returns |
| Effect event param `attribute_fqon` is empty | Handler logs "dropping (no-op)" and returns |
| Effect event param `target_id` is `0` (default) | Handler hits the `has_game_entity(0)` check, logs "missing", returns |

P3.4 will extend the stale-event set to cover:
- target removed mid-batch while a follow-up `game.attack` is also pending
- attacker removed while a follow-up `game.attack` is pending
- duplicate effect events at the same timestamp (deduplication is
  implicitly handled because the effect handler always writes
  `current - amount` from the latest curve value, so duplicates compound
  correctly)

## P3.3 readiness

P3.3 must:

1. Add a generic `Live::on_attribute_change` (or equivalent) threshold
   listener that derives a `DeathEvent` when the post-write Health is
   `<= 0` for any attribute named in the Live ability.
2. Make `ApplyDiscreteEffectHandler` dispatch the `DeathEvent` (instead
   of inline `remove_game_entity`).
3. Add idempotency guards:
   - `HP <= 0` triggers death at most once per entity (entity-level flag)
   - same-timestamp duplicate effects → still one death
   - dead target receiving additional effect → no second death
4. Add demo 12 covering all of the above.

The P3.2 report explicitly pins the readiness:
- The inline removal code is isolated in a single `if` block at
  `apply_discrete_effect.cpp:120-128` (well-marked with "P3.2 temporary"
  in both the source and the runtime log line).
- The `Live::on_attribute_change` callback infrastructure already exists
  (used by demo 11 for the HP-change counter); P3.3 wires a NEW
  threshold-driven callback into the same Live storage.
