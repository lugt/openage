# William Wallace Mission 1 — P3.1 Lifecycle Characterization

**Phase:** P3.1 — Characterize current lifecycle  
**Branch:** `mvp/william-wallace`  
**Date:** 2026-07-29  
**Companion spec:** `docs/mvp/specs/WW_MISSION1_SCENARIO_RUNTIME_SPEC.md`  
**Companion plan:** `docs/mvp/specs/WW_MISSION1_DEVELOPMENT_PLAN.md`

P3.1 records the **CURRENT** behavior of the Mission 1 combat
lifecycle by inspecting GameState / EventLoop / Entity state directly
in C++ (NOT by parsing demo 7 logs). The recorded outputs are
CHARACTERIZATION data — they pin the implementation's current shape
so P3.2-P3.4 refactors can preserve (or intentionally break, with
failing tests) the user-visible semantics.

---

## Mechanism

`bin/run test --demo gamestate.tests.simulation_demo 10` (demo 10).

Demo 10 builds the runtime the same way as demo 7:
`GameSimulation -> set_modpacks({de2_base, ww_mvp}) -> initialize()
-> start()`. It then:

1. Reads the Mission Pack from
   `assets/converted/ww_mvp/campaign/william_wallace/` via
   `openage.scenario.writer` output (P2.7).
2. Inspects `state->get_named_entities()` to verify the
   `ScenarioObjectId -> GameEntityId` mapping produced by
   `register_named_entity`.
3. Reads the Live component's Health attribute directly via
   `Live::get_attribute_value(time, fqon)` to confirm the pre-attack
   HP and post-hit HP without log parsing.
4. Issues one `game.send_command` event with `command_t::ATTACK`
   targeting the enemy.
5. Drives the EventLoop with `peek_next_event_time()` /
   `reach_time(next, state)` and reads HP after each batch.
6. When `state->has_game_entity(target_id)` flips to `false`, records
   the removal timestamp.
7. Logs each hit with `t` and `HP` as CHARACTERIZATION data; the
   demo PASSES as long as the characterization data is captured,
   even if the data drifts from the prior demo 7 numbers (drift is
   reported, not failed).

## Pins (must remain stable across P3.2 / P3.3 / P3.4 refactors)

1. `ScenarioObjectId -> GameEntityId` mapping is
   placement-list-order (PlayerVillager=0, PlayerTownCenter=1,
   EnemyVillager=2). P3.4 must not change this without a migration
   test.
2. The first hit lands immediately when the move completes
   (cooldown was initialised to the attack start time). P3.2 must
   preserve this so the demo's `hit at t=13.28976` line remains
   valid.
3. Each subsequent hit lands `cooldown` seconds after the previous
   one. P3.2 / P3.3 must preserve the 2.0 s gap.

## TEMPORARY characterizations (must NOT be固化 as permanent)

- **Objective polling**: the demo records that
  `WilliamWallaceMission01ObjectiveController::on_update(now)` is
  called once per event batch via
  `simulation->tick_objective_controller(now)`. This is the H0.5
  TEMPORARY DEBT (per `docs/mvp/reports/phase-h0.5-driver-report.md`
  §3). P4 must REPLACE this with a `MissionCompletedEvent`
  lifecycle hook so the controller subscribes to the event, not to a
  per-batch poll. **The polling API and the
  `tick_objective_controller` method must be REMOVED in P4, not
  kept as a compatibility hook.**

- **Inline death-and-remove** in AttackHandler (line 180-188 of
  `gamestate/event/attack.cpp`): `gstate->remove_game_entity(...)` is
  called from inside the event handler. P3.4 must convert this to a
  deferred RemovalEvent so removal is safe under the spec §6.6
  invariant.

- **Direct Health mutation**: `target_live->set_attribute(time,
  health_fqon, new_value)` writes the new HP directly without
  routing through `ApplyDiscreteEffect`. P3.2 must add the
  `ApplyDiscreteEffect` path; the demo's HP numbers (25→19→13→7→1→-5)
  are the CURRENT behaviour and may change by exactly the per-hit
  damage value if P3.2 adds a separate "damage applied" event
  whose effect subtracts the damage.

## P3.2 / P3.3 / P3.4 readiness

P3.2 (route damage through `ApplyDiscreteEffect`) may change the
`Health` numbers (the new effect path might emit a
`HealthDepletedEvent` or similar between hits) but must preserve:
- the 5 hits to kill an HP=25 target with damage=6
- the 13.29 s move time (pathing is orthogonal)
- the 2.0 s cooldown gap

P3.3 (generic death): may emit a `DeathEvent` instead of inline
removal; must preserve removal_t and the post-removal objective
state.

P3.4 (deferred removal): must remove the inline
`gstate->remove_game_entity(...)` from the AttackHandler and route
removal through a deferred RemovalEvent; must preserve removal_t
within the event-batch boundary (i.e. removal_t must equal
last_dispatched_t of the same batch, not the start of the next).

---

## Stale-attack-after-death (deferred to P3.4)

The AttackHandler requires an `EventEntity` handle (not GameEntity)
to invoke directly. Demo 10 records the death/removal timestamp;
P3.4's deferred-removal test will exercise the stale-event path
because the deferred RemovalEvent triggers a re-evaluation of the
attacker's cooldown clock against an absent target.

The CURRENT behaviour (per demo 7 log evidence):
```text
AttackHandler: target 2 not found; target gone, stopping attack
```
i.e. the AttackHandler logs a warning and stops the attacker's
attack cycle. P3.4 must preserve this and add it as a regression
test.
