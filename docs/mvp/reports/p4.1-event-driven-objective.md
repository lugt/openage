## 6. Before/after objective call chain

**Before (H0.5 temporary debt, polling):**

```text
GameSimulation::run() loop (every tick)
  -> GameSimulation::tick_objective_controller(current_time)
    -> WilliamWallaceMission01ObjectiveController::on_update(now)
      -> poll step.check(state)   # closure: has_game_entity(tid) for each target
      -> if predicate fires, mark_completed + advance
```

Polling ran once per simulation tick (H0.5; `objective_poll_count`
instrumented in demo 7). Mission 1 was declared "complete" only when
the next per-batch poll happened to observe `has_game_entity(target)
== false`. This was a state-coincidence finish, not an event finish.

**After (P4.1, event-driven):**

```text
DeathEvent fires (HP -> 0)
  -> deferred to RemovalEvent (P3.4)
    -> game.removal
      -> RemovalEventHandler::invoke
        1. GameState::remove_game_entity(target_id)
        2. for each observer: observer(target_id)
             -> WilliamWallaceMission01ObjectiveController::notify_entity_removed(target_id)
                 -> if id in step.removal_targets_remaining:
                        erase from set
                        if set empty: mark_completed + advance
```

`on_update` is now a no-op for event-driven steps; the polling
predicate is preserved only for not-yet-event-driven missions
(2-5, which still return false from their `check` closures and
have no removal targets). The H0.5 `tick_objective_controller` and
its `objective_poll_count` instrumentation are removed.

## 7. Event subscription design

The openage `EventLoop` stores handlers in a `std::unordered_map`,
keyed by the handler's name. It supports one handler per event
name; `insert` on duplicate is a silent no-op. This means a
naive second `add_event_handler("game.removal", ...)` is dropped.

The user brief allowed the minimum-viable extension
"`RemovalEventHandler` notifies registered dependency" if a second
handler cannot be registered. We chose that path:

* The production `RemovalEventHandler` exposes
  `add_observer(observer_t)`.
* `GameSimulation::register_objective_handler` runs after the
  objective controller is created (the controller is created AFTER
  `init_event_handlers` because the controller needs the scenario
  FQON to select the right mission factory), and registers a
  closure that forwards each removal to
  `objective_controller->notify_entity_removed(target_id)`.
* The observer list is the SOLE extension point for new consumers
  of `game.removal`. The legacy GameState mutation behaviour is
  unchanged.

This is the smallest possible patch to the openage event
infrastructure that satisfies the "no separate callback bus" rule.

## 8. ScenarioObjectId resolution

`create_mission_1_trigger` resolves the placed-instance FQON
`ww_mvp.campaign.william_wallace.mission_01.EnemyVillager` to a
runtime `entity_id_t` via `GameState::get_entity_id_by_instance`.
If the lookup fails (no instance registered) the trigger is built
with an empty removal-target set; the step then never completes
(closed-failed, no false victory).

`notify_entity_removed` does NOT rely on the placed-instance FQON
or the ScenarioObjectId; it uses the runtime `entity_id_t` that the
production `RemovalEventHandler` already extracted from the event
param map. The ScenarioObjectId remains the source of truth for
"which placed instance is the target"; the event handler is the
transport that carries the runtime id to the trigger. The trigger
matches the event payload to the registered target set by id,
which is exactly the "stable identity" rule the brief asked for.

## 9. Idempotency semantics

* **Duplicate removal events** for the same target id: the
  production `RemovalEventHandler` drops them (the GameState
  mutation succeeds once, then `has_game_entity(target_id) == false`
  and the handler short-circuits). Observers are not called for
  duplicates, so the controller never sees a duplicate
  `notify_entity_removed`.
* **Stale removal events** for an entity that was never in the
  active step's target set: `notify_entity_removed` runs the
  `std::find` and silently returns no-op.
* **Multi-target objectives**: `removal_targets_remaining` is a
  `std::vector<entity_id_t>`; each matching `notify_entity_removed`
  erases one entry; the step completes only when the vector is
  empty.
* **Once a step is `completed`**, subsequent
  `notify_entity_removed` calls are no-ops (the early return at
  the top of the method).

Demo 14 pins 7, 8, 10, 12, 13 verify these properties.

## 13. P4.2 entry point

P4.2 (the next planned milestone) is "wire the trigger execution
side". The Mission 1 trigger currently completes via
`game.removal`; the next step is to make the *completion* do
something useful (e.g. publish a `MissionCompletedEvent` for the
HUD, or transition the game state machine to `MissionComplete`).
The P3-handoff report recorded this as the open follow-up. The
infrastructure added by P4.1 (event-driven step + observer
callback on the production removal handler) is the natural
extension point for P4.2.
