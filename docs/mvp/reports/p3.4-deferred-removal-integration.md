# William Wallace Mission 1 — P3.4 Deferred Removal Integration

**Phase:** P3.4 — Deferred dead-entity removal  
**Branch:** `mvp/william-wallace`  
**Date:** 2026-07-29  
**Companion spec:** `docs/mvp/specs/WW_MISSION1_SCENARIO_RUNTIME_SPEC.md`  
**Companion plan:** `docs/mvp/specs/WW_MISSION1_DEVELOPMENT_PLAN.md`

P3.4 moves the entity-removal call from `DeathEventHandler` (which
synchronously called `gstate->remove_game_entity` during P3.3) into a
dedicated `RemovalEventHandler` that owns the only `remove_game_entity`
call in the codebase. The dispatcher's call stack no longer mutates
the GameState entity container mid-iteration.

---

## Before / after call chains

### Before (P3.3)

```
ApplyDiscreteEffectHandler (game.apply_discrete_effect)
 → set_attribute
 → if (new_value <= 0):
     → create_event("game.death")
DeathEventHandler (game.death)
 → mark_dead
 → gstate->remove_game_entity(target_id)            [SYNCHRONOUS REMOVAL]
 → stop_attackers(target_id)
```

### After (P3.4)

```
ApplyDiscreteEffectHandler (game.apply_discrete_effect)
 → set_attribute
 → if (new_value <= 0):
     → create_event("game.death")
DeathEventHandler (game.death)
 → mark_dead
 → create_event("game.removal")                     [DISPATCH]
 → stop_attackers(target_id)
RemovalEventHandler (game.removal)                  [NEW, SOLE OWNER]
 → has_game_entity(target_id) check (idempotency)
 → gstate->remove_game_entity(target_id)
```

`DeathEventHandler` and `ApplyDiscreteEffectHandler` no longer mutate
the GameState entity container. `RemovalEventHandler` is the **only**
handler that calls `remove_game_entity`. The dispatcher's call stack
returns to `reach_time` between the death-event and the
removal-event invokes, so the iteration is safe.

| Aspect | Value |

## Stale-event safety guarantees

| Scenario | Result |
|---|---|
| Death fires → removal fires (normal case) | Removal sees alive entity → remove_game_entity → log |
| Two death dispatches (same time) | First mark_dead returns true → dispatch removal. Second mark_dead returns false → no-op, no second removal dispatched |
| Duplicate removal dispatches | `has_game_entity` returns false → silent no-op |
| Stale attack follow-up after removal | `AttackHandler` sees `has_game_entity(target)` false → "target gone, stopping attack" log + clean stop |
| Stale effect event after removal | `ApplyDiscreteEffectHandler` sees `has_game_entity(target)` false → "stale event, dropping (no-op)" log |
| Stale death event after removal | `DeathEventHandler` sees `has_game_entity(target)` false → "stale event, dropping (no-op)" log |
| Stale removal event after removal | `RemovalEventHandler` sees `has_game_entity(target)` false → silent no-op |

## Runtime indexes cleaned by removal

P3.4 cleans the **primary GameState entity storage** via
`gstate->remove_game_entity`. The MVP Mission 1 does not wire any
secondary runtime indexes (no spatial index, no pathfinding cache,
no collision grid, no selection set), so there are no additional
indexes to invalidate. P0-F-4 (EntityFactory `unhandled ability parent`
warnings) is unaffected — those warn at entity-creation time, not at
removal time.

| Index | Wiped by removal | Notes |
|---|---|---|
| `GameState::game_entities` (entity_id_t → GameEntity) | YES | via `remove_game_entity` |
| `GameState::named_entities` (ScenarioObjectId → entity_id_t) | NO | the historical instance identity is preserved; `has_game_entity(id)` now returns false, but `get_entity_id_by_instance(fqon)` still returns the historical id so trigger/objective systems (P4) can resolve "the EnemyVillager that was killed" |
| `EntityFactory::activity_cache` | NO | the activity graph is per-entity; the entity shared_ptr is dropped when the GameState map erases, the cache entry is dropped with it |
| `AttackHandler::active attackers` | YES (indirectly) | `DeathEventHandler::stop_attackers` runs BEFORE the removal event fires; it iterates the GameState map and calls `Attack::stop_attack()` for every attacker pointing at the dead target |
| Pending attack follow-ups in EventLoop queue | YES (implicitly) | the follow-up `game.attack` event is queued at the simulation time; when it fires, `AttackHandler` runs the `has_game_entity(target)` check and drops cleanly |
| Pending effect events in EventLoop queue | YES (implicitly) | the follow-up `game.apply_discrete_effect` event is queued; when it fires, the handler sees `has_game_entity(target)` false and drops |
| RenderEntity | NO | the renderer-facing pointer (`render_entity`) on GameEntity is dropped when the shared_ptr to GameEntity is dropped |

| Invariant | Implementation |
|---|---|

| Stale attack / effect / death / removal events are safe | each handler has its own `has_game_entity` safety check |

## Stale-event semantics summary (P3.4 final)

| Handler | Stale-event check | Behaviour |
|---|---|---|
| `ApplyDiscreteEffectHandler` | `has_game_entity(target_id)` | "stale event, dropping (no-op)" + return |
| `DeathEventHandler` | `has_game_entity(target_id)` | "stale event, dropping (no-op)" + return |
| `RemovalEventHandler` | `has_game_entity(target_id)` | silent no-op (avoids log spam) |
| `AttackHandler` | `has_game_entity(target_id)` | "target gone, stopping attack" + `attack_comp->stop_attack()` |

The `target_id` lifetime guarantee: it is a 32-bit integer
allocated by `EntityFactory::next_entity_id()` and never reused in the
same session. `has_game_entity(target_id)` is the authoritative
"is this id still alive?" check.

## P4.1 minimum entry

P4 (trigger runtime + event-driven objectives) starts with **P4.1**:
**introduce a `MissionCompletedEvent` lifecycle hook** that the
`WilliamWallaceMission01ObjectiveController` subscribes to, and remove
the H0.5 `tick_objective_controller` polling API.

The P3 work provides the entry points P4 needs:

1. **`game.removal` event** — the objective controller can subscribe
   to removal events on the EnemyVillager instance FQON, replacing the
   poll-on-`on_update` check.
2. **`GameState::get_named_entities()`** — the controller already uses
   this to find the EnemyVillager's runtime id; the lookup is
   unchanged (P3.4 preserves the historical ScenarioObjectId →
   entity_id_t mapping even after removal).
3. **`Live::on_attribute_change` / `on_threshold_drop`** — the
   controller can subscribe to HP transitions on the EnemyVillager
   for live HUD updates (out of scope for P4.1 but the API exists).

The H0.5 TEMPORARY DEBT items that P4 must remove:
- `GameSimulation::tick_objective_controller(time)` method
- `WilliamWallaceMission01ObjectiveController::on_update(now)` polling
- `objective_poll_count` instrumentation in demo 7
- The TEMPORARY annotation in `p3.1-lifecycle-characterization.md` and
  `ww_mission1_lifecycle.cpp` log line

## Lifecycle diagram (P3 final)

```
[User/AI send_command]
    │
    ▼
game.send_command (SendCommandHandler)
    │ enqueues AttackCommand into attacker's CommandQueue
    │ creates game.attack event
    ▼
game.attack (AttackHandler)
    │ pops AttackCommand; sets attack_comp->start_attack(...)
    │ range check:
    │   ├─ out of range: Move::move_default + follow-up game.attack
    │   └─ in range + cooldown elapsed:
    │       ├─ creates game.apply_discrete_effect event
    │       └─ schedules follow-up game.attack at t+cooldown
    ▼
game.apply_discrete_effect (ApplyDiscreteEffectHandler)
    │ stale-event safety
    │ Live::set_attribute(time, health_fqon, current - amount)
    │ if (new_value <= 0):
    │   └─ creates game.death event
    ▼
game.death (DeathEventHandler)
    │ idempotency gate: entity->mark_dead() (one-shot)
    │ creates game.removal event
    │ stop_attackers(target_id)
    ▼
game.removal (RemovalEventHandler)
    │ has_game_entity idempotency
    │ gstate->remove_game_entity(target_id)
    ▼
[entity gone from GameState]
```
