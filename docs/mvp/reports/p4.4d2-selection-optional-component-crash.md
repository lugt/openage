# P4.4D.2 — Selection Crash on Entities Without Optional Components

**Date:** 2026-10-19
**Branch:** `mvp/william-wallace`
**Status:** `SELECTION_OPTIONAL_COMPONENT_CRASH_FIXED`

## 0. Scope

The Mission 1 windowed launch (`scripts/run_ww_mission1.sh`) terminated with

```
FATAL: terminate has been called
std::exception of type std::out_of_range: unordered_map::at: key not found
```

as soon as the player dragged a selection box over the map. The failure
was reproducible on every attempt (log:
`logs/ww_mission1_20261009_002501.log`).

This report records the root cause, the fix, and the regression test.

## 1. Root cause

The crash was **not** a null pointer dereference. It was
`std::unordered_map::at()` throwing on a missing key, inside the
simulation thread, on the drag-select path.

Call chain (from the crash backtrace, innermost first):

```
GameEntity::get_component(component_t)          game_entity.cpp:48
  └─ this->components.at(type)                  ← throws std::out_of_range
SelectionModel::wire_health_callback(entity)    selection_model.cpp:272
SelectionModel::replace_selection(...)
SelectionModel::set_multi_selection(...)
input::game::Controller::set_selected(...)
input::game::setup_defaults(...)::$_3           ← drag-select binding
event::DragSelectHandler::invoke(...)
event::EventLoop::execute_events(...)
```

**Why the component was missing:** the entity factory mounts an `Attack`
component only for entities whose nyan abilities include
`ApplyDiscreteEffect` or `RangedDiscreteEffect`
(`libopenage/gamestate/entity_factory.cpp:335-342`). A **TownCenter is a
building with no attack ability**, so it never gets an `Attack`
component. Selecting the TownCenter therefore asked for a component the
entity legitimately does not have.

**Why this was a bug and not just a missing feature:** the codebase
already intended `get_component` to be a nullable lookup. Almost every
call site in the tree is written as

```cpp
auto x = std::dynamic_pointer_cast<Component>(entity->get_component(TYPE));
if (x) { ... }
```

— i.e. the author expected a null result and wrote a null check for it.
The implementation used `.at()`, which throws *before* the null check can
run, making every one of those checks dead code. `SelectedEntityView`
even documents the intended contract:

> `selected_entity_view.h:44` — *"If the entity is unknown or has no
> Live component, the view's fields are nullopt / 0."*

> `selected_entity_view.h:87` — *"Attack component (e.g. a non-combat
> building) return nullopt / ..."*

The implementation violated its own documented contract.

## 2. Fix

### 2.1 `GameEntity::try_get_component()` (new)

A non-throwing lookup returning `nullptr` when the component is absent,
alongside the existing throwing `get_component()`. `get_component()` is
kept throwing on purpose: it is used by ~12 engine-internal call sites
(`move.cpp`, `spawn_entity.cpp`, `drag_select.cpp`, …) that do **not**
null-check the result. Making it globally nullable would have converted
those loud exceptions into silent null-pointer dereferences.

### 2.2 `GameEntity::get_component()` diagnostics

The throwing lookup now names the entity and the component instead of
emitting a bare `unordered_map::at: key not found`:

```
entity 3 has no Attack component
```

`component::to_string()` was added in
`libopenage/gamestate/component/types.{h,cpp}` for this purpose. The
exception type changed from `std::out_of_range` to
`openage::error::Error` (which derives from `std::runtime_error`); no
code in the tree caught `std::out_of_range`, so this is behaviour-
preserving for every caller.

### 2.3 Presenter layer uses the nullable lookup

- `SelectionModel::wire_health_callback()` — the crash site. An entity
  without an `Attack` or `Live` component simply has no health attribute
  to watch, so the wiring is skipped instead of aborting the selection.
- `SelectedEntityView` (5 lookups) — same latent bug: selecting a
  TownCenter would have thrown at the `ATTACK` lookup.

`SelectionOverlay` and `Presenter::render()` already used the
`has_component()` guard and were left untouched.

## 3. Regression test

`libopenage/gamestate/demo/selection_optional_component_demo.cpp`
(**demo 50**) pins the behaviour:

1. **Premise** — the TownCenter really has no `Attack` component.
2. `SelectionModel::set_multi_selection()` on it does not throw, and
   selects it.
3. `SelectedEntityView` on it does not throw, and reports empty attack
   fields (per its documented contract).
4. A mixed multi-selection (TownCenter + villager) still wires the
   health callback for the villager — the fix must not disable health
   wiring for entities that *do* have an `Attack` component.

Red/green verified: with the fix stashed, demo 50 reproduces the exact
original exception (`std::out_of_range: unordered_map::at: key not
found`); with the fix applied, all five pins pass.

## 4. Build environment drift (unrelated to the crash, blocked the work)

While adding demo 50, the build stopped configuring. Root cause: two
pieces of the environment had moved since the last successful build
(2026-08-06) —

- Homebrew's `cmake` was upgraded to **4.4.0** (the project was
  configured with CMake 3.x). CMake 4.x refuses to `try_compile` C++
  module sources unless the compiler can scan the import graph, and
  Apple clang has no `clang-scan-deps`.
- Upstream **nyan** `master` advanced to a version that requires
  C++26 and probes for C++ module support
  (`3f9915d buildsystem: require C++26 compilers and probe for module
  support`, merged in `9686f34`). The project tracks nyan via
  `fetch_project(... GIT_TAG ${NYAN_CLONE_VERSION})`, whose default is
  `origin/master`, so re-configuring pulled that version in.

Fix: pin nyan to the commit the working build used (`f462a1f`, nyan
master as of 2025-09-14). **This is now the default in the repository**,
not just a command-line override — `libopenage/CMakeLists.txt:91` reads:

```cmake
if(NOT DEFINED NYAN_CLONE_VERSION)
	set(NYAN_CLONE_VERSION f462a1f)
endif()
```

so a fresh `./configure` picks the pin up instead of nyan master. It
takes effect on re-configure because `fetch_project` runs the
ExternalProject update step on every configure
(`buildsystem/DependencyFetch.cmake:75-80`); no manual `git checkout` is
needed.

Configure into the **real** build directory, not the `bin` symlink:
`CMAKE_BINARY_DIR` ends up in the paths of generated code
(`codegen_scu.gen.cpp`), and a symlinked path produces broken includes.

```bash
cmake -S . -B .bin/clang++-debug-Oauto-sanitize-none
make -C bin -j$(sysctl -n hw.ncpu)
```

## 8. Hardening: the SIGSEGV variant of the same bug

The original crash was a thrown exception, not a segfault. Auditing the
same code path for the *segfault* variant turned up a worse one, two
lines away from the fix:

```cpp
auto attack = entity->try_get_component(component_t::ATTACK);
if (attack) {                                       // checks the BASE ptr
    std::dynamic_pointer_cast<Attack>(attack)       // may be nullptr
        ->get_health_attribute_fqon();              // <-- SIGSEGV
}
```

`try_get_component` returns a `shared_ptr<Component>`, so `if (attack)`
is true as soon as *any* component is mounted. The cast result is never
checked. Whenever the enum and the concrete class disagree, the null
pointer reaches the dereference. Three such sites existed:

- `selected_entity_view.cpp:69` (the ATTACK→Attack cast above)
- `presenter.cpp:471` (POSITION cast in the selection-overlay render loop)
- `selection_model.cpp` (two casts, reachable via drag-select)

### 8.1 Why this is `try_get_component_as<T>()`, not an `assert`

The original ask was to add `assert`s. Asserts cannot deliver the
requested guarantee here, for three reasons found by inspection:

1. **They are compiled out in release.** `buildsystem/HandleCXXOptions.cmake:140`
   sets `-DNDEBUG` for the release configuration, so an assert provides
   zero protection there.
2. **They still crash.** An assert fires SIGABRT; the game dies either
   way, just with a clearer message.
3. **They cannot be tested.** Demo 50 asserts on a deliberate mismatch
   aborts the process at the assert, so the subsequent pins never run —
   the test cannot verify the guard it is testing.

So the guard throws `openage::error::Error` instead, which survives
`-DNDEBUG` and is observable by a test:

```
entity 0 has a Attack component, which is not a
openage::gamestate::component::Live (requested as component_t::Attack)
```

Both halves matter. `to_string(type)` names the enum; `util::typestring<T>()`
names the requested C++ class. Reporting the enum alone yields "has a
Attack component where a Attack component was requested" — true, and
useless, because the enum cannot tell you which cast is wrong.

`try_get_component_as<T>()` keeps the two failure modes distinct, which
the raw pattern conflates:

| Condition | Result | Why |
|---|---|---|
| Component not mounted | `nullptr` | legal state; caller handles it |
| Mounted but not a `T` | throws `error::Error` | programming error |
| Correct | typed pointer | — |

An `assert` version (`try_get_component_as_strict<T>()`) is available for
call sites that want a hard stop in debug, but engine code uses the
throwing form.

### 8.2 Demonstration

Demo 50 pin 5 requests `Live` through the `ATTACK` enum — a deliberate
mismatch, since the villager *does* have an `Attack` component. It
requires an error rather than a misleading `nullptr`, then confirms a
correctly-typed lookup on the same entity still returns a pointer, so
the guard is not simply "reject everything".
